Принято. Это критический баг в потоке аутентификации (Auth Flow). Приложение ведет себя так, будто пользователь залогинен, хотя на самом деле это "призрак".
Диагноз (First Principles)
Проблема: UI показывает интерфейс для залогиненного пользователя (InboxDeck, PlanList), но этот UI нефункционален.
Корневая причина: Наш серверный компонент (app/layout.tsx) по умолчанию считает, что юзера нет (user равен null), и передает в StoreInitializer пустой массив [].
Ошибка в UI: Клиентские компоненты (app/page.tsx) видят isLoading: false (так как пустой массив загрузился мгновенно) и items: []. Они не знают разницы между "задач нет" и "пользователя нет". Поэтому они рендерят интерфейс для залогиненного пользователя с пустым списком.
Почему нельзя ничего сделать: Любая попытка свайпнуть или добавить задачу падает, потому что у "призрака" нет user_id для отправки запросов в базу.
Предлагаемое решение: "Стена аутентификации" (Auth Wall)
Нам нужно четко разделить состояние приложения на "Публичное" (экран входа) и "Приватное" (основной интерфейс).
Новая логика:
На уровне layout.tsx (Сервер):
layout.tsx по-прежнему проверяет await supabase.auth.getUser().
Он получает объект user.
Ключевое изменение: Он передает на клиент не только items, но и самого user.
На уровне StoreInitializer.tsx (Клиент):
Наш Zustand store будет иметь новое поле: user: User | null.
StoreInitializer при запуске запишет в store и initialItems, и initialUser.
На уровне корневого компонента (Клиент):
Мы создадим компонент-обертку, например, <AuthGuard />, который будет рендериться в layout.tsx.
Логика <AuthGuard />:
Он слушает user из useStore.
Если user есть (не null), он рендерит дочерние компоненты (children — то есть, наше основное приложение).
Если user равен null, он рендерит только страницу логина и больше ничего.
Как это будет выглядеть для пользователя:
Новый пользователь: Заходит на fleeets.app. Сервер отдает ему HTML. Компонент <AuthGuard /> на клиенте видит, что user равен null, и показывает ему страницу /login. Основной интерфейс (с карточками, навигацией) даже не пытается рендериться.
Авторизованный пользователь: Заходит на fleeets.app. Сервер видит его куки, отдает HTML с данными user и items. <AuthGuard /> на клиенте видит, что user есть, и пропускает его к основному интерфейсу.
Преимущества этого подхода:
Безопасность и предсказуемость: Нет состояния "полу-логина". Либо ты внутри, либо снаружи.
Чистота кода: Логика проверки авторизации находится в одном месте (AuthGuard), а не размазана по всем страницам.
Производительность: Мы не рендерим лишние компоненты для анонимных пользователей.
